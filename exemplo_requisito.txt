Painel de Monitoramento de Clima

A proposta é criar um painel full stack para consulta climática usando
React no frontend e Node.js no backend.

A aplicação deve permitir que o usuário consulte informações
meteorológicas de qualquer cidade de forma simples, rápida e com uma
interface visualmente agradável. A ideia é que seja uma experiência
moderna, responsiva e preparada para funcionar bem em dispositivos
mobile, tablet e web.

A arquitetura precisa respeitar uma regra importante desde o início: o
frontend nunca deve consumir a API da Open-Meteo diretamente. Toda
comunicação com serviços externos deve passar obrigatoriamente pelo
backend, que será o responsável por intermediar requisições, resolver
geolocalização e retornar os dados necessários para a interface.

O fluxo esperado é simples: o usuário digita o nome de uma cidade, o
frontend envia essa informação para o backend, o backend consulta a API
de geocoding da Open-Meteo para transformar o nome da cidade em latitude
e longitude e, em seguida, usa essas coordenadas para consultar a API de
previsão do tempo. Depois disso, devolve os dados ao frontend, que
apenas renderiza as informações.

As integrações externas usadas serão:

Geocoding: https://geocoding-api.open-meteo.com/v1/search

Clima: https://api.open-meteo.com/v1/forecast

O backend pode retornar os dados seguindo o mesmo formato da Open-Meteo,
sem necessidade de remodelagem complexa neste momento.

A aplicação deve expor um endpoint principal:

GET /api/weather?city=

Os retornos esperados são:

-   200 quando a consulta for bem sucedida
-   400 quando houver parâmetros inválidos
-   404 quando a cidade não for encontrada

Ao acessar a aplicação, o usuário já deve cair diretamente no painel
principal pela rota “/”, sem telas intermediárias.

A estrutura do projeto deve ser separada em dois diretórios
independentes:

/frontend para a aplicação React /backend para o servidor Node.js

O painel deve mostrar as condições climáticas atuais da cidade
pesquisada, incluindo temperatura, umidade, velocidade do vento, índice
UV e precipitação.

Também deve exibir previsão por hora, contendo temperatura e
precipitação em formato gráfico interativo, além de uma previsão para os
próximos sete dias mostrando mínima, máxima e volume de chuva de forma
comparativa.

A experiência visual é uma parte central do projeto.

A interface precisa ser responsiva e adaptada para mobile, tablet e web.
O painel deve usar cards visuais com ícones animados representando o
clima, skeleton loading enquanto os dados estão carregando e feedback
visual claro durante buscas.

A identidade visual deve mudar dinamicamente conforme as condições
climáticas. Céu limpo pode usar tons azulados, tempo nublado tons
acinzentados e chuva tons mais escuros e frios.

O índice UV deve ser apresentado como uma barra gradiente variando entre
verde e vermelho.

Os cards da previsão semanal devem mostrar visualmente a variação entre
mínima e máxima através de indicadores gráficos simples.

A busca deve ser feita por um campo de texto simples, sem autocomplete
nesta versão.

Também deve existir um botão para usar a geolocalização do navegador e
consultar automaticamente o clima da localização atual do usuário.

Caso a cidade não seja encontrada, a aplicação deve exibir uma mensagem
amigável orientando nova tentativa.

Se houver falha de comunicação, o usuário deve receber feedback claro e
uma opção de tentar novamente.

Existem algumas restrições técnicas importantes que precisam ser
respeitadas.

Não deve existir nenhum tipo de cache HTTP entre frontend e backend.

No backend, ETags devem ser desabilitadas e todas as respostas precisam
retornar Cache-Control: no-store.

No frontend, toda chamada fetch deve usar explicitamente cache:
‘no-store’.

A estratégia de comunicação entre frontend e backend precisa ser
definida de forma explícita. Pode ser usado proxy do dev server (como
Vite proxy) ou comunicação via URL absoluta com CORS habilitado, mas
isso deve estar documentado e consistente em todo o projeto.

As portas usadas pelo frontend e backend precisam estar claramente
documentadas tanto para ambiente de desenvolvimento quanto para
produção.

O backend deve possuir configuração explícita de CORS definindo origens
aceitas, métodos permitidos e headers autorizados. Durante
desenvolvimento pode aceitar qualquer origem, mas isso precisa estar
documentado.

Depois da implementação, a validação será feita primeiro testando
diretamente as APIs da Open-Meteo via curl para conferir estrutura e
retorno esperado.

Depois disso, será testado o endpoint interno do backend para garantir
que a resposta está sendo repassada corretamente ao frontend.

Algumas coisas estão fora de escopo e não devem ser implementadas agora:

-   tema claro/escuro
-   autocomplete de cidades
-   comentários no código
-   remodelagem avançada do payload da Open-Meteo
-   qualquer chamada direta da API externa pelo frontend

A entrega esperada é um scaffold funcional, limpo e bem separado, pronto
para servir como base para evoluções futuras.
